# 无限制帧率导致整屏不刷新 / 像卡死 —— 原因分析

日期：2026-10-31
环境：Windows 11，NVIDIA RTX 5060 Laptop（8 GB，驱动 591.86），Forge 1.20.1-47.4.26，Java 21，TACZ-先锋-0.7 整合包（106 mods）

## 结论
**不是某个模组的 mixin 冲突，也不是新加的两个模组导致的。**
根因是 **「最大帧率 = 无限制（260）」+「垂直同步关闭」**：

1. Minecraft 1.20.1 原版 `Minecraft.runTick()` 里：

       Window.updateDisplay();           // 垂直同步在这里换缓冲
       int fps = this.getFramerateLimit();
       if (fps < 260) {                  // 260 = 无限制档，直接跳过限帧
           RenderSystem.limitDisplayFPS(fps);
       }

   所以把“最大帧率”调到 260（界面显示“无限制”）时，游戏**根本不再调用限帧器**；再关掉垂直同步，渲染循环就全速跑。
2. 这个整合包的优化 mod 很多（Embeddium、Accelerated Rendering、Bons and Furious、Flerovium、Brute Force Culling 等），
   在 854×480 的小窗口里可以轻松跑到 **1000+ FPS**（实测 HUD：1169 / 平均 878 / 最大 1186）。
3. 在这种帧率下，GPU 显示队列 / Windows DWM 桌面合成被饿死 → **整个桌面停止刷新**（表现为“电脑卡死”，
   但游戏进程其实还活着）；关闭游戏进程后 DWM 恢复，所以看起来“直到程序关闭才恢复”。
4. 打开垂直同步后，缓冲交换被显示器刷新率节流（通常 60/144/165 Hz），不会再出现这种桌面饿死。
5. 整合包里几个“帧节奏/限帧”mod（FramePacer、Ixeris 的 enhanced_fps_limiter、Bons 的 frame_pacing、
   Collections of Optimizations 的 paceFramesBeforeSwap）在 **fps ≥ 260 时都不会介入**：
   原版根本不调用限帧器，它们就没有机会节流——所以指望它们防止“无限制帧率卡死”是无效的。

## 证据
- 用户实例旧配置（22:03 的副本）：`enableVsync:false`、`maxFps:260`；
- 该配置下真实客户端副本运行时 HUD 实测 1000+ FPS（截图 evidence/crawl-repro/01-world.png 等）；
- 2026-10-31 00:18–00:28 副本运行中，桌面整体停止刷新，直到关闭游戏进程后恢复；
- 用户自己把垂直同步打开后不再出现；当前正式实例 options.txt 已是 `enableVsync:true`，所以现在正常。

## 处理建议
1. **保持垂直同步开启**（已验证有效）。
2. 另外把“最大帧率”从“无限制(260)”改成 **120 / 144 / 165（按显示器刷新率）**，双保险；
   即使哪天垂直同步被关掉，也不会再冲到 1000+ FPS。
3. 不建议为了无限制帧率去改 NVIDIA 控制面板 / 关闭 HAGS 等驱动设置：收益极小、风险更高。
4. 若一定要测极限帧率，至少全屏 + 垂直同步，或小窗口短时间测试，并准备随时结束进程。
